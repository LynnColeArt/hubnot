## Native audit admission, export, and promotion

**Keep two different closures.** Ordinary explicitly selected code/actor/proposal/memory histories and legacy code dependencies retain full Git closure. Audit dependencies retain the exact signed `audit.pack` closure: target commit plus snapshot tree/blobs, policy/source commit plus required path-proof trees/blobs. Commit parents and unrelated proof-tree siblings can intentionally be absent. Do not add `auditObjectRoots` to `projectDependencyRoots` and then call ordinary `rev-list --objects`/full-history copying on them.

Existing canonical seams:

- `B/audit_protocol.go:711` `auditDependencyObjectIDsAt`: no parent traversal; policy/source path proofs and target `--no-walk` snapshot.
- `:238` `auditPackObjectIDsAndSizes`: compressed/expanded/object-count bounds, no deltas, checksums, exact object sizes and IDs; `:768` `validateAuditPackBinding` requires exact signed closure; `:816` `validateAuditObjectShapesAt` checks actual edge types while allowing deliberate missing edges.
- `:352` `importAuditPack`: isolated temporary object DB, `index-pack --fsck-objects` for object syntax, exact binding, then installation into the explicitly supplied DB. It deliberately does not require complete commit ancestry.
- `B/store.go:210` `loadStoredEventAt` verifies signatures/tree/attachments and calls `importAuditPack`; `B/quarantine.go:856` `validateQuarantinedActor` uses that loader. `:961` `replicationEventDependency` delegates audits to `validateAuditRelationshipAt`, including recorded policy roles and exact authorization/request/source links. Retain these validators rather than recreating audit permission logic.

**Smallest coordinated bridge maintenance** belongs in `C/project_snapshot.go`, preserving existing exported signatures:

1. In `StageProjectSnapshot`, finish raw object hashing/budgets and run ordinary full Git structural checking while the bare DB contains only supplied ordinary material, **before any native reader unpacks `audit.pack`**. Then load/admit native histories, enforce exact ordinary selected/dependency closure against the original supplied ID set, and validate audit relationships through existing native admission. Running blanket `fsck` after audit unpacking risks demanding intentional missing parents/siblings; running it before unpacking and native admission afterward avoids imposing that requirement. Audit object shape/binding checking must remain in `importAuditPack`, not disappear with the moved `fsck`.

Migration must enforce its saved `Limits.GitObjects/GitObjectBytes/GitTotalBytes` over the union of ordinary and expanded dependency IDs across the selection, with shared IDs counted once. Per-pack limits alone do not bound many packs in one migration. Do not discount objects merely because the destination already has them. Validate exact pack binding after this measurement.
3. `ExportProjectSnapshot:48` currently calls `projectDependencyRoots:516`, which calls `validateQuarantinedActor` on the **source**. Combined with WP02 this unpacks objects into the source object DB, contradicting read-only planning/export. Inspect signed histories in disposable private object staging instead. One workable sequence is: copy the bounded selected ordinary closure to private inspection staging; use canonical native readers there to discover legacy code dependencies; read those explicitly identified ordinary dependencies from the source; build the final raw spool; run the final clean quarantine admission sequence above. No source ref, worktree, config, or object DB changes. Avoid a second event/signature validator.

Copy ordinary roots through that boundary and/or copy the admitted explicit object-ID union without revision traversal, or reinstall each already validated exact audit pack in the destination before promotion. ## Optional write unions and StrictJSON

`C/internal/migration/snapshot.go:269` `StrictJSON` supplies UTF-8/surrogate, duplicate/null, depth/trailing-token and case-exact field checks. `exactKeys:369` requires every struct field even with `omitempty`; therefore it cannot directly decode a valid `RemoteRef` with only `id` or only `receipt`, nor an issue/comment create with absent `target`. Requiring both branches or emitting null violates the frozen contract.

**Preferred smallest WP05-only solution:** keep the helper unchanged. `Intent.Payload` and `BoundWrite.Payload` are `json.RawMessage`; `exactKeys` explicitly leaves those opaque. Keep `StrictJSON` for enclosing required Plan/Intent/etc. fields. The sole new write-schema validator in `internal/migration/plan.go` can call `StrictJSON(payload, &map[string]json.RawMessage)` to reuse all lexical protections, then validate explicit required/allowed key sets and nested objects before typed decoding/canonical marshal. Maps bypass reflected struct key enumeration; this means the WP05 validator, not the map decode, must close every level.

- `RemoteRef`: exactly one present key, `id` or `receipt`; literal ID must be bounded/nonempty; receipt must have exactly `intent_id`,`field`, with declared confirmed predecessor and `remote_id|remote_key|revision` field allowlist. Check presence before decoding: an empty `id` alongside `receipt` is still a forbidden second branch.
- Issue/comment creates: `target` absent, not null or an empty object. Updates: valid target required. Comment parent always required. Retain every required title/body/state/type/labels/assignees field even when its value is empty. Revalidate the resolved actual payload, then persist canonical bytes/digest before in-flight state.
- Do not duplicate Unicode/token logic or loosen required source record/content fields. Ordinary JSON decoding only follows shared strict lexical checks and explicit closed key validation. Apply the same pattern to new optional reconciliation shapes if needed.

Alternative shared maintenance: teach `exactKeys` that only explicitly `omitempty` fields may be absent, retaining all other required fields; then tag only new optional write branches. This is a small generic change, but touches WP04 ownership and broadens helper semantics. It still needs separate presence-aware exclusivity/action validation, so it buys less than the WP05-only approach. Never make all pointer/string/empty fields optional globally.

- WP05 owns `migration_native.go` and engine/plan/progress/local/journal files; it does **not** own `project_snapshot.go`, its tests/docs, or `internal/migration/snapshot.go`. Coordinate a narrowly recorded sequential handoff with WP04's owner before bridge maintenance. Root should include those exact surfaces in the authorized maintenance scope; no speculative broad lane rebuild or frontmatter edits.
- All canonical native validators are root-package functions and directly callable from WP05 root files. `internal/migration` must remain independent of root/provider clients; no exported API redesign is necessary for audit validation.
- `B/quarantine.go:1708` `promoteReplicationRefs` permits accepted actor/proposal/memory refs only and operates on the current repository. It does not implement arbitrary-destination code refs. WP05 must define its destination-scoped code-observation mapping and guarded transaction in its own native bridge rather than smuggle source branches through this helper or update local signing streams. Persist old values/destination identity in plans. Do not silently adopt active policy or overwrite destination identity/worktree state.
- `Archive`/`ProjectSnapshot`/`ProjectQuarantine` own temporary spools and require `Close`; the apply engine must keep its verified blob source alive across bounded application, or persist the immutable source needed for resume. No source refresh or adapter-private parent map.

## Focused regression expectations for the implementing owner

Cover an audit-only selected actor history whose signed pack legitimately omits target/policy parents and unrelated proof siblings; successful offline archive/stage/apply and later keyless audit reads; exact signed bytes; malformed/missing proof objects, wrong edge types, bad binding/log/signature/roles/missing signed supplier refusal; aggregate expanded-object limits before unpacking; ordinary incomplete code history still refused; source refs/worktree/**object DB** unchanged by export; no anchor or signing-identity creation; stale destination/uncertain-ref recovery preserving visibility. For JSON cover absent create target, required update target, each RemoteRef branch, both/neither/empty extra branch refusal, and existing unknown/duplicate/null/Unicode/missing-required source rejection. These are proposed regressions, not tests executed in this investigation.
